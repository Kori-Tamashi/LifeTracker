# Journal — извлечения и подтверждение

Первый бизнес-срез D-012.1, правила BR-04. Реализованы Domain и Application сценарий review; это не подключённый пользовательский дневник/локальный ИИ.

## Поведение

- Предложение содержит профиль, разговор, source event, model manifest и типизированные кандидаты: событие, упоминание человека, гипотеза. Субъект (владелец/другой человек) и отрицание/неопределённость сохраняются отдельно.
- EvidenceSpan берёт цитату из предоставленного исходного текста сообщения по проверенному UTF-16 диапазону, хранит ID/revision сообщения и не допускает разрезания surrogate pair. Сам текст summary и классификация кандидата остаются выводом извлекателя: цитата доказывает происхождение, не истинность интерпретации. Смысл отрицания/чужого опыта не угадывается строковыми эвристиками.
- По умолчанию proposal pending и не входит в память. Autoconfirm принимает весь валидный набор, сохраняя гипотезы гипотезами. Невалидный набор целиком отклоняется.
- Confirm/edit/reject возможны только из актуального pending с expected revision. Edit заменяет набор после полной проверки; пустой набор не используется как скрытое удаление. Каждое решение создаёт новую immutable revision, исходная не меняется.
- Принятую гипотезу нельзя стереть повторным reject. Несогласие/пересмотр интерпретаций относится к будущему Insights, не маскируется удалением extraction.
- Новая версия исходного сообщения помечает зависимое извлечение stale, не удаляя историю; более старый повтор/другое сообщение не инвалидирует его. Retrieval допускает только **последнюю** accepted/non-stale revision. Старые принятые версии в истории не являются активным RAG-контекстом.
- Упоминания с одинаковым текстом не объединяются автоматически. Person identity resolution/owner-approved merge и Episode dedup ещё не реализованы.

## Application граница

ReviewExtractionHandler проверяет профиль/команду/decision, снимок edited candidates и semantic fingerprint, возвращает сохранённый receipt при повторе. Repository port должен атомарно проверить expected revision, append историю и сохранить receipt. Scope ключа — профиль + extraction + review operation. Повтор с тем же ключом и иной семантикой — конфликт; повтор с новым command ID, но той же семантикой возвращает первый receipt. Порядок edited candidates не меняет семантику набора. Другой профиль не получает запись.

Infrastructure не вызывается напрямую, ORM/HTTP/AI SDK в Domain/Application отсутствуют. Единственный repository-порт описывает review, а не универсальный CRUD. Общий Clock — Application.Abstractions.

Тесты используют синтетический repository double и проверяют бизнес-сценарии, receipt replay, конфликт и cancellation. Они **не доказывают** SQLite atomicity/concurrency: real repository contracts — следующий отдельный срез. Архитектурные assembly guards включают Journal.

## Следующие бизнес-срезы

1. Хранение разговоров/сообщений/предложений/review history и общий real-store contract. Текст источника берётся из авторизованного owner-message store, а не из вывода модели; caller обязан проверять роль/текущую source revision перед созданием evidence. SourceRevised связывается с изменением сообщения транзакционно.
2. Подключение локального extraction gateway только после Q-AI-TEXT: schema/semantic corpus (отрицание, чужой опыт, неопределённость), latency/footprint/license. Пока модель unqualified; выдуманный parser или cloud fallback не добавлены.
3. Текстовый/голосовой пользовательский путь и отображение review. Нормативный HTTP DecideExtraction ещё 503; новая возможность не объявляется enabled.
4. Insights: независимые Episode IDs, пороги повторений/дней, противоречия, disagreement и RAG. Eligibility policy этого среза не заменяет retrieval/index или психологический анализ.

Этот пакет не меняет schema, миграции, running app, release tags или существующие профили. Конкретные transport DTO/Contracts появятся при добавлении внешней границы; Application commands сейчас внутренние.
