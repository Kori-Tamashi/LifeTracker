# Чистая архитектура и SOLID

> Baseline 1.0: нормативные значения и закрытые решения — [BR-01–10](../requirements/baseline-rules.md). Этот документ — вспомогательное представление; прежние пометки «предложено/уточнить» не отменяют зафиксированный baseline. Реализуемость интеграций подтверждается отдельными gates.

Статус: требование применять Clean Architecture/SOLID подтверждено; конкретная раскладка ниже предложена. [Диаграмма зависимостей](diagrams/uml-clean-architecture.puml).

## Слои

| Слой | Содержание | Разрешённые зависимости |
| --- | --- | --- |
| Domain | Агрегаты, инварианты, объекты-значения, чистые политики | Стандартная библиотека и минимальный shared kernel |
| Application | Сценарии, транзакционные границы, порты, DTO результата | Domain и публичные application-контракты модулей по явному списку |
| Infrastructure | Репозитории, БД, очередь, файловое хранение, интеграции, модели | Application + Domain, внешние SDK |
| Presentation / adapters | macOS, Telegram, локальный API, маппинг запросов | Application contracts; не конкретный репозиторий |
| Composition Root | Создание графа объектов, конфигурация, запуск | Все нужные реализации; только здесь связываются внешние адаптеры с портами |

Интерфейсы сценариев и технических зависимостей (`Clock`, `UnitOfWork`, `InferenceGateway`) живут в Application у потребителя. Доменный сервис/политика находятся в Domain только если выражают предметное правило, а не orchestration. ORM-модель, HTTP DTO и доменная сущность — разные роли; конвертация делается на границе. Не переносим SDK-типы, IQueryable, пути файлов и JSON-объекты модели внутрь домена.

Модули образуют вертикальные области, каждый с этими слоями. Это модульная чистая архитектура, а не одна гигантская папка Services. Для R1 реализуются только нужные модули; будущие области не требуют заранее создавать пустые классы.

## SOLID в проверяемых правилах

| Принцип | Пример Life Tracker | Как проверяем |
| --- | --- | --- |
| SRP | BalancePolicy выбирает/считает состояние; RecordAssessment координирует запись; контроллер преобразует канал | Сценарные unit-тесты и ревью причин изменения; контроллер не содержит формулы |
| OCP | Новый канал или банк добавляется адаптером существующего порта | Contract tests для новой реализации; доменные правила не изменяются ради формата SDK |
| LSP | Репозиторий/fake сохраняют одинаковые правила отсутствия записи, версий, идемпотентности и ошибок | Один набор поведенческих contract tests для реализаций; fake не обещает транзакцию, которой не поддерживает |
| ISP | ReadAssessmentHistory, AssessmentWriter, InferenceGateway имеют нужные потребителю операции | Нет интерфейса «умеет всё», методов с UnsupportedOperation и обязательного наследования неиспользуемых API |
| DIP | Сценарий зависит от портов, БД и модель реализуют их | Автоматическая проверка import/project graph; Infrastructure не импортируется из Domain/Application |

Не вводим интерфейс для каждого класса, фабрику без варианта построения или наследование ради повторного использования полей. Чистая BalancePolicy может быть обычной функцией/классом без интерфейса.

## Автоматические архитектурные тесты

После выбора языка проверять реальные компиляторные/import зависимости: Domain не зависит от внешних слоёв и framework; Application не зависит от Infrastructure/Presentation; модули не читают чужие таблицы и внутренние пакеты; циклы между модулями запрещены; внешние DTO не появляются в доменных публичных сигнатурах. Разрешения composition root задаются точечно, не широким исключением всей папки.

Нарушение — обязательный failure CI. Тест должен обнаруживать специально внесённую запрещённую зависимость в изолированном тестовом fixture, чтобы формальная настройка не давала ложный зелёный результат. Конкретная библиотека проверок будет выбрана со стеком.

## Использование учебного примера

В предоставленном Eventor изучены проекты Domain/Application/DataAccess/Web, project references, LocationService и интерфейс, категории тестов и CI. Полезны направление зависимостей, инъекция репозитория, разделение Unit/Integration/E2E и обязательные проверки слияния. Стек .NET/Angular не выбран для Life Tracker автоматически.

В примере интерфейсы прикладных сервисов размещены в Domain, а Application содержит в том числе JWT/options зависимости. Для Life Tracker прикладные порты отделяем от чистого домена; UI- и инфраструктурную конфигурацию не переносим в бизнес-правила. Наблюдения сделаны по выбранным файлам, не являются полной оценкой качества Eventor. Исходные файлы учебного проекта не копируются и не меняются.
