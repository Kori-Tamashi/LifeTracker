## ALG-01 — выбор состояния

Вход: активные ревизии наблюдений одного профиля, `now`, версия политики. Выход: четыре выбранные версии/unknown, баланс, уровень и происхождение.

```text
for metric in [energy, mood, anxiety, physical_wellbeing]:
    eligible = current revisions where accepted and not invalidated
               and 0 <= now - observed_at < 6h
    manual = eligible where source_kind == self_report
    inferred = eligible where source_kind == ai_estimate
    chosen[metric] = newest(manual) else newest(inferred) else unknown
if any chosen is unknown: return undefined balance + known metrics
normalized = [energy, mood, 10 - anxiety, physical_wellbeing]
balance = min(normalized)
level = excellent if balance >= 9 else good if >= 7.5
        else satisfactory if >= 6 else attention
valid_until = min(chosen.observed_at + 6h)
```

Новизна определяется временем состояния, затем последовательностью ревизии, затем стабильным ID. Исправленная прежняя ревизия исключается, даже если её значение лучше. Приоритет ручной оценки действует, пока она актуальна, независимо от более нового ИИ-предположения. Вычисленная инверсия тревоги не сохраняется как пятое самостоятельное наблюдение. Чтение проверяет TTL, поэтому проснувшийся UI не показывает старый «хороший» баланс до тика scheduler.

Сложность: O(n) по отобранным наблюдениям; индекс `(profile, metric, source_kind, observed_at)` ограничивает окно. Проверки: AC-001–005, ровно 6 часов, будущая запись, совпавшие времена, stale ручная + fresh ИИ, исправление события. Применение TTL к ИИ и tie-break — уточнения проекта.

## ALG-02 — durable jobs

Приём: проверить владельца/формат → записать media durable → в короткой транзакции insert inbox, job, outbox и receipt под unique source key → commit → подтвердить приём. Повтор того же ключа/содержимого возвращает receipt; изменённый payload под тем же ключом даёт conflict. Для локальных запросов ключ создаёт клиент; hash не заменяет намерение пользователя.

Claim: короткая write-транзакция выбирает `ready_at <= now`, учитывая приоритет и возраст; атомарно задаёт `lease_owner`, `lease_until`, увеличивает `fence`. Модель работает вне транзакции. Завершение допускается только при совпадении fence, действующего lease и версий входа. Heartbeat продлевает lease условным update. Истёкший worker не может сохранить результат, даже если другой worker ещё не успел закончить.

Предложение retry: максимум 5 автоматических попыток для timeout/unavailable; `delay = Uniform(0, min(15min, 5s * 2^(attempt-1)))`. Ошибки validation/auth/conflict не повторяются слепо. После лимита — failed с сохранённым входом и явным повтором после исправления. Wake-up переводит просроченные leases в готовность, не обнуляет attempts и квоты. Fairness: после трёх интерактивных задач обслуживать одну готовую фоновую; тяжёлых inference-задач одновременно не более одной до замеров. Это стартовая политика, подлежащая нагрузочной проверке.

При crash после записи файла, но до commit — orphan, удаляемый только после grace period и проверки отсутствия ссылок. При crash после commit, но до ответа — повтор возвращает receipt. Telegram offset продвигается только после локального принятия всех предыдущих updates; неизвестные типы явно учитываются, не блокируя offset бесконечно. Источник Telegram хранит недоставленные updates не более 24 часов: выключенный надолго Mac не обеспечивает бессрочную очередь на стороне сервиса ([Bot API](https://core.telegram.org/bots/api#getupdates)).

## ALG-03 — голосовой диалог

1. Принять аудио через ALG-02, определить conversation и язык, проверить доступность локальных моделей/места.
2. Локально распознать речь с временными сегментами. При низкой разборчивости спросить уточнение, не создавать факт из неподтверждённого текста.
3. В быстрой ветке получить контекст ALG-05 и начать содержательный ответ. Отдельная job выполняет полное структурированное извлечение; пользователь видит, что оно ещё идёт. Цель 15 секунд относится к началу ответа, а не завершению всех индексов и отчётов; транскрипция входит в измерение.
4. Извлекать candidates по схеме: observation/event/person-link/interpretation, времена, цитаты, unresolved fields. Проверять каждую ссылку на исходник и допустимость диапазонов. Неполная дата остаётся неопределённой до уточнения.
5. Сопоставить эпизоды и людей; неоднозначное совпадение не сливать автоматически. Повтор рассказа связывать с прежним эпизодом, а не считать новым действием.
6. При autoconfirm принять валидные candidates; иначе сохранить pending extraction. Отклонённые и pending не входят в активный RAG. Принятие ИИ-предположения не меняет его source_kind.
7. Commit принятых версий + outbox → пересчёт/индекс → итоговое резюме и ссылки на основания. Результат старого fence или устаревшей версии не применяется.

Инвариант: быстрый ответ не сообщает «я записал», пока запись не committed. Сбой фонового извлечения не стирает уже доставленный ответ и остаётся видимым. Беседа может продолжаться; ответные сообщения коррелируются по conversation/turn, поздний ответ не вставляется как ответ на другой вопрос.

## ALG-04 — исправление оснований

Вход: entity ID, expected revision, исправление и причина. В транзакции проверить optimistic concurrency → создать ревизию → сменить current pointer → пометить зависимые выводы stale → outbox. Граф зависимостей хранится по revision ID; циклическая зависимость выводов запрещена при создании. Обход affected graph O(V+E), с дедупликацией посещённых узлов.

Синхронный State пересчитывается при чтении; тяжёлые выводы rebuild выполняются топологически/по готовности актуальных оснований. Commit проверяет, что набор оснований всё ещё current. Старый вывод остаётся историей с причиной замены; пометка несогласия не удаляет факт. Поисковая выдача повторно проверяет current/stale в авторитетной БД даже при отстающем индексе. GameEffect пересматривается компенсацией, без удаления исходного эффекта и без двойного восстановления XP.

## ALG-05 — retrieval и интерпретации

Начальный retrieval: фильтр профиля/accepted/current → явные связи с Person/Episode → полнотекстовые кандидаты FTS5 → объединение с недавними релевантными событиями → дедупликация по episode/revision → ограничение token budget. Стартовые лимиты-предложения: до 30 кандидатов, до 8 эпизодов и 2 000 токенов retrieved context; исключить переполнение окна модели. Ранжирование сначала по явному совпадению сущности, затем FTS-рангу, затем давности; несопоставимые численные оценки не складывать произвольными весами.

FTS5 не обещает полноценной русской семантики; качество проверяется recall@k на корпусе. Если не достигнут согласованный порог, добавить локальные embeddings через отдельный порт и повторить оценку. Vector DB не обязательна для первого RAG. Связи и evidence хранятся в SQL, не в единственном необъяснимом векторе.

Новый общий вывод о повторяющемся поведении: найти независимые эпизоды, исключить пересказы/отрицания/чужой опыт → минимум три различных эпизода минимум в два разных дня как **предложенный** стартовый порог → показать примеры и противоречащие наблюдения → качественная уверенность/неопределённость. Порог — правило приложения, не клинический критерий. При меньшем объёме допустима заметка об отдельной ситуации, не устойчивая черта. Новая информация может ослабить вывод; ИИ не получает права замораживать мнение навсегда.

## ALG-06 — бюджет

Все суммы одной валюты; base currency conversion допускается только по явному правилу FX, иначе сводка неполна. Деньги — точные единицы/decimal, не binary float.

План: `P = sum(expected_income)`; процентная статья `P * percent / 100`, округление до minor unit. Остаток округления распределять методом наибольших остатков со стабильным tie-break ID, чтобы итог не превышал P. Обязательства и накопления резервируются отдельно от расходов; переназначение расхода в reserve недопустимо.

Предлагаемые показатели (не завершённая бухгалтерская модель):
- `cash_available` — текущие положительные ликвидные собственные средства без кредитного лимита, с вычетом известных удержаний; активы портфеля/вклады исключены, пока не ликвидны.
- `free_now = cash_available - unpaid_reserved_obligations - protected_savings - other_active_reserves`. Резерв исключается при оплате, иначе расход был бы вычтен дважды.
- `plan_remainder = approved_spending_plan - actual_consumption`; может быть отрицательным и не равен наличным средствам.
- `daily_guide = max(0, min(free_now, flexible_plan_remaining)) / remaining_calendar_days`, включая текущий день. Это ориентир доступных уже денег, не прогноз с учётом будущей зарплаты.

Сопоставить фактический доход с ожидаемым по источнику/сумме/дате; неоднозначность показать. До срока поступления отсутствие факта не считается недополучением. После срока предложить revision плана; текущий план менять только при подтверждении.

Закрытие месяца: убедиться в свежести источников → получить snapshot/revision → сверить переводы/возвраты/долг → предложить перевод **не зарезервированного ранее** положительного остатка в учётную копилку → сохранить closing record. При неполноте данных закрытие provisional. Поздняя операция создаёт restatement и компенсирующую проводку, не второй перенос остатка. При дефиците не списывать копилку автоматически без отдельного правила.

Инвестиции: события сделок/комиссий/налогов сохраняются независимо от личного бюджета, ввод/вывод между собственными счетами не становится потреблением. Методы TWR/MWR, cost basis, FX и расчёт налоговых обязательств требуют отдельного проекта; до него показывать только исходные данные и явно определённые расчёты, не обещать полный налоговый калькулятор.

## ALG-07 — автономные квесты

ИИ генерирует структурированные candidates, rules engine проверяет цель/допустимость/нагрузку/срок/дубликаты. Отказ проверки не перекладывается на пользователя как пропуск. Одно assignment не заменяет consent на произвольные действия системы.

Стартовая политика-предложение: максимум 3 активных ежедневных квеста, нагрузка 1–3 points каждый, бюджет 4 points/day. При явном режиме болезни/восстановления — максимум один optional квест стоимостью 1, без штрафов; медицинские назначения и финансовые траты не генерировать. При неизвестной ситуации не увеличивать нагрузку по догадке.

Адаптация раз в неделю: оценивать completion только среди известных исходов, исключить no-data, paused, технический сбой. Нужно минимум 5 известных исходов; иначе сохранить бюджет. Выполнение ≥80% в двух последовательных окнах и отсутствие режима восстановления → предложенный автоматический рост бюджета на 1 (предел 6); <50% → уменьшить на 1 (минимум 1). Ограничение числа/очков действует после ИИ, не обходится его текстом.

Игровая модель v0.1 (П): XP — исторический прогресс; обычное выполненное задание даёт 10 XP, +1 связанного игрового атрибута (шкала 0–100). Нет данных не штрафуется. Со второго последовательного **подтверждённого** пропуска — −1 атрибута, максимум −5 на одну серию квеста; XP/достижения не отнимаются. Болезнь/пауза обрывает серию без штрафа. Успех обрывает серию и даёт обычную награду, без дополнительного двойного восстановления. Отсутствующий игровой baseline остаётся unknown до отдельно согласованной инициализации, а не искусственно «здоровым».

Эффект уникален по occurrence, evidence action и версии применения. Исправление выполнения создаёт reversal старого эффекта и новую запись; числовые пределы применяются к проекции, не теряют историю исходных delta. Прогресс квеста не меняет ручные самооценки ALG-01.

## ALG-08 — уведомления

Вход: trigger с reason key/expiry, профиль, now, состояние доставки. Рассчитать local day/quiet hours. Ответ на запрос пользователя не проактивное напоминание. Если expired — drop с причиной. Если quiet — отложить на 09:00, но после defer вновь проверить expiry/актуальность. После сна объединить совместимые актуальные triggers, старые не нагонять.

В одной транзакции проверить unique reason, зарезервировать один слот из трёх общих reminder events состояния/квестов, создать NotificationEvent и две Delivery. Если quiet переносит на другой день, слот резервируется в день плановой фактической отправки, не в исходный день. Если событие истекло до первой попытки и ни одна доставка не произошла — reservation освободить атомарно. После первой доставки один слот остаётся использованным независимо от сбоя второго канала. Budget alert имеет отдельный тип и ключ `(budget_revision, category, threshold_band)`; корректировка плана не должна спамить повтором той же причины.

Новая попытка Delivery не резервирует слот. HTTP timeout после отправки — ambiguous outcome: exactly-once не обещается, повтор ограничивается; редактирование известного message ID предпочтительнее создания нового там, где это возможно.

## ALG-09 — фото блюда

Принять фото, удалить лишние EXIF из рабочей копии, локально предложить ингредиенты/порцию → сверить с локальным справочником пищевой ценности. Источник справочника и право распространения ещё не выбраны; без него цифры модели остаются низконадёжным estimate, не измерением.

Если ингредиент/масса сильно меняют итог — не более двух коротких вопросов. `nutrient_total = sum(grams_i / 100 * nutrient_per_100g_i)`. Масса и состав имеют интервалы, поэтому итог тоже диапазон; неизвестные масло/соусы явно отмечаются. Если данных недостаточно — сохранить блюдо без КБЖУ. Не выводить медицинские нормы белка/калорий автоматически. Повтор фото не создаёт второй приём пищи без отдельного подтверждённого события. Изменение массы пересчитывает ту же запись и зависимые эффекты.

## ALG-10 — резервирование и удаление

Backup: barrier против retention уникальных медиа → snapshot БД через backup API → manifest только ссылок snapshot → копирование/проверка immutable media hashes → integrity/referential checks → atomic rename manifest в completed → release barrier. Пока копия не completed, она не участвует в ротации. Старые копии удаляются только после успешной новой и проверки доступного диска. Models/cache/index не копируются. Restore в изолированный каталог: проверка manifest/hashes/schema → integrity check → пересборка индекса → smoke → остановка писателей и атомарное переключение. Миграция требует предмиграционной completed копии.

Retention: семь дней после committed успешного извлечения; нет активных jobs/pending подтверждения/backup pin → проверены summary и короткие Evidence → tombstone → удаление исходного файла → повторно безопасная фиксация статуса. Не обещать полную смысловую сохранность. Политика семи дней остаётся проектным предложением. Сбой извлечения не даёт права удалить оригинал по одному возрасту.

Дисковый лимит: учитывать файлы, БД/WAL, модели, копии и контейнерные артефакты, не только `var/`; проверять preflight до загрузки модели/приёма большого медиа. При нехватке сначала очищать восстанавливаемый cache по политике; не уничтожать единственное основание/копию. SDK и build cache выделить в отчёте отдельно; отнесение внешней Docker VM к лимиту нужно уточнить перед обещанием 10 ГБ.

## ALG-11 — импорт

Адаптер получает batch с checkpoint; сохраняет сырой payload только в разрешённом локальном журнале с retention → валидирует схему → нормализует единицы/время/source key → upsert новой версии при реальном изменении → фиксирует batch/checkpoint/outbox атомарно. При частичном сбое checkpoint не перепрыгивает незафиксированную часть; повтор безопасен.

Apple metrics: сравнивать перекрывающиеся интервалы/ID, не складывать агрегат Watch и тот же агрегат iPhone как независимые шаги. Отсутствие прав/данных — unknown. Финансы: pending и posted операции сопоставлять, а не удваивать; transfer pairing не по одной сумме, а по источнику, счетам, ссылкам/дате с проверяемой неоднозначностью. Возврат не является зарплатой. Если нет устойчивого автоматического адаптера, R3 blocked — никаких фиктивных заглушек, выдаваемых за интеграцию.

## Программа проверки алгоритмов

Каждый ALG получает unit/property/contract и fault scenarios по [стратегии](../../delivery/testing-strategy.md). Особые свойства: идемпотентность (ALG-02/11), отсутствие stale evidence (04/05), сохранение денег и отсутствие двойного резерва (06), нет штрафа за unknown (07), quota ≤3 при конкурентной отправке (08), restore с теми же ссылками (10). В этой итерации проверяются модели/документы; продуктовые алгоритмы ещё не реализованы и не протестированы исполнением.
