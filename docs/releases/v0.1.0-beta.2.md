# LifeTracker 0.1.0-beta.2 — кандидат для ручной проверки

Статус: подготовка кандидата в develop, **не опубликованный GitHub Release**. Публикация main/tag выполняется отдельным release-процессом после оценки кандидата. Это B1 State/lifecycle/backup, не полный R1.

## Изменения относительно beta.1

- Revalidation после wake без лишнего Core; сохранение workspace при временной потере связи.
- Offline создание, проверка и восстановление профиля через «Профиль → Резервные копии».
- Опциональные суточные копии после 09:00 Москвы: startup, tick раз в минуту и wake. Семь снимков, verify/restore перед ротацией, локальный disk guard.
- Координированная пауза собственного Core/журнала; отправка временно блокируется, workspace сохраняется. Чужой Core автоматически не останавливается.
- Настройки папки/порта/автокопий изолированы по beta-версии. Beta.2 не перенаправляет preferences установленной beta.1. Автоматического переноса данных нет.

## Получение кандидата

Требования прежние: Apple Silicon, macOS 26+, .NET 10 с Microsoft.AspNetCore.App 10.0; Docker не требуется. Подпись ad-hoc, без notarization. Сборка не меняет Login Items и не устанавливается поверх beta.1 автоматически.

При изменении release metadata в develop workflow `Beta release` выполняет полные candidate gates и сохраняет `beta-assets-<SHA>` в Actions на семь дней. Это artifact для проверки, не релиз; `evidence.json` содержит `delivery: candidate artifact only`. Проверить SHA/версию/evidence и SHA256SUMS. Artifact download может требовать входа в GitHub. Assets не содержат пользовательского профиля.

Локально из чистого develop:

```sh
python3 tools/package_macos.py build
python3 tools/package_macos.py verify var/build/LifeTracker.app
```

Результат — отдельный `var/build/LifeTracker.app`. Полностью завершить установленную beta.1 перед запуском кандидата. Можно открыть пакет из Finder; перемещать в Программы для этой проверки не нужно. Выбрать **новую отдельную папку**, например `var/beta-2`; прежний профиль не использовать. Это предотвращает конфликт порта/писателей, а изоляция preferences не заменяет изоляцию файлов.

## Короткий проверочный сценарий

1. Убедиться, что интерфейс показывает beta.2. Новый профиль: неизвестные показатели/баланс. Записать синтетическую энергию 8, исправить её на 6 с причиной, полностью завершить и открыть снова. История и исправление должны сохраниться.
2. Закрыть окно и открыть его через menu bar. Проверить сохранность состояния. Это ещё не подтверждённый OS/GUI gate.
3. В «Резервные копии» остановить подключение. Создать копию в отдельном каталоге `var/backups`, проверить её, восстановить в новую папку `var/restored-beta-2`. Выбрать восстановленный профиль на экране подключения, проверить запись. Повтор восстановления в существующую папку должен отказать, сохранив её.
4. Выбрать отдельный каталог автокопий, например `var/automatic-backups`. После 09:00 Москвы дождаться tick. Внутри появится `<profile-id>/daily-YYYY-MM-DD`. До 09:00 отсутствие копии ожидаемо; часы macOS ради теста не менять. Повтор в тот же день не должен создать второй суточный снимок.
5. Для проверки формы: открыть несохранённую форму перед первой due-попыткой (удобно включить автокопии при открытой форме). Дождаться паузы; введённые поля должны остаться, отправка во время паузы недоступна, после возврата Core запись сохраняется один раз. **Визуально этот сценарий пока не принят.**
6. При удобном естественном сне Mac проверить возврат подключения после пробуждения; не менять системные настройки питания или автозапуск ради автоматического теста.

Результаты сообщать по шагам: pass/fail/not run, ожидаемое и фактическое, версия macOS. Не прикладывать credential, профиль, личные записи или полный диагностический архив. После проверки полностью завершить кандидат; beta.1 остаётся установленной, её папка и preferences не менялись кандидатом при использовании отдельного профиля.

## Ограничения и критерий дальнейшего выпуска

GUI-клики, открытая форма при backup, реальный sleep/login, desktop orphan, предмиграционные копии, общий footprint 10/20GB, target RPO/RTO и energy ещё не квалифицированы. Неудачный restart Core может закрыть несохранённую форму; pending-команда остаётся на диске. Автокопии требуют запущенного desktop, собственного Core и включённой настройки. При low-space/corruption/коллизии процесс отказывает, а предупреждение нельзя считать успешной копией. Бюджет managed копий — 2GB на профиль, это не общий лимит приложения.

ИИ, питание, финансы, квесты, Telegram и Apple-интеграции отсутствуют. Полный R1 scope не сокращается. Candidate handoff не выдаётся за пройденную приёмку. Перед main/tag: результаты ручной проверки, разбор выявленных дефектов, успешный exact-main release workflow с backup evidence; опубликованный beta.1 tag/assets не перемещаются.

## Исправление по ручной проверке: Finder metadata

Первый кандидат отказывал в суточной копии после появления `.DS_Store` внутри managed каталога. Исправленный кандидат допускает только обычный файл Finder metadata в каталоге и snapshot, исключает его из manifest/inventory артефактов и не переносит в восстановленный профиль. Ссылки, каталоги с таким именем и прочие неизвестные файлы по-прежнему запрещены. Удалять metadata или существующие копии пользователю не требуется. При запущенном старом кандидате новая сборка предоставляется в отдельном `var/build/finder-fix/LifeTracker.app`; перед переключением полностью завершить старый экземпляр. Версия beta.2 остаётся candidate, исходный SHA указан в package manifest/Actions artifact.
