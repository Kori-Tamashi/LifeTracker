# Стратегия тестирования и критерии качества

> Baseline 1.0: нормативные значения и закрытые решения — [BR-01–10](../requirements/baseline-rules.md). Этот документ — вспомогательное представление; прежние пометки «предложено/уточнить» не отменяют зафиксированный baseline. Реализуемость интеграций подтверждается отдельными gates.

Статус: требование полного тестирования подтверждено; конкретные пороги ниже предложены. «Полное» означает проверку требований, рисков, интеграций и отказов, а не обещание отсутствия любых дефектов или универсальные 100% строк.

## Уровни

| Набор | Проверяет | Зависимости / запуск |
| --- | --- | --- |
| Architecture | Слои, циклы и границы модулей | Реальный граф сборки/import, каждый PR с кодом |
| Domain unit | Диапазоны, выбор источника, срок, баланс, квоты, деньги, эффекты | Fake clock, без БД/сети/модели, каждый PR |
| Application unit | Оркестрацию, запреты, конфликты, отмену и обработку ошибок | Контрактные fakes портов, каждый PR |
| Adapter contract | Поведение репозитория/провайдера и схемы транспорта | Общий набор для fake и реальной реализации, каждый PR адаптера |
| Persistence integration | Реальную СУБД, транзакции, unique constraints, миграции, очередь, lease/outbox | Та же технология хранилища, что в продукте; изолированная БД/каталог |
| API/channel integration | Маппинг, авторизацию владельца, повторную доставку, версии DTO | Локальный стенд, симулятор Telegram/банка/Apple без личных токенов |
| E2E | Сквозной пользовательский результат установленной сборки | Чистый синтетический профиль; основные сценарии каждого релиза |
| macOS UI | Навигацию, ввод, состояния загрузки/ошибки, закрытие окна | macOS runner / целевой Mac; UI automation после выбора стека |
| Reliability | kill/restart в точках записи, disk full, сон/пробуждение, network timeout | Fault injection, без обращения к реальному профилю |
| Backup/migration | Снимок, восстановление, совместимость версий и откат при неуспехе | Профили предыдущего релиза, синтетические данные |
| AI evaluation | Извлечение, различение фактов/гипотез, источники, неопределённость, ложные повторы | Локальная фиксированная модель и версионированный synthetic corpus |
| Performance | UI/query, первый ответ ИИ, память/диск/энергия | Фиксированные стенд/настройки; целевой Mac для приёмки 15 секунд |
| Publication | Ссылки, состав Git, отсутствие личных путей/файлов и секретов | Автоматический базовый gate + ручное чтение diff |

Unit-тест ORM с in-memory заменой не доказывает корректность реальных транзакций/SQL. Живые внешние сервисы — отдельный диагностический smoke, не обязательная зависимость обычного PR. Отсутствие доступа показывается blocked/unverified, а не «интеграция протестирована».

## Обязательные сценарии R1

AC-001–005: 0/10, шаг 0,5, частичный ввод, ручной приоритет, ИИ fallback, unknown, граница 6 часов, четыре порога, совпадение времени, будущие/поздние записи и пересчёт. AC-008–011: сохранение квот после перезапуска, два канала/одно событие, тихие часы, фон после закрытия окна, полная остановка, сон/пробуждение, durable очередь и восстановление.

Дополнительно: конфликт ревизии, повтор/конфликт idempotency key, исправление одного показателя без стирания остальных, отсутствие моделей не блокирует ручной R1, отказ источника не даёт ложное значение. Не создавать assertions только на число вызовов mock, если пользовательский результат не проверен.

## AI evaluation R2

Раздельно измерять распознавание речи, извлечение полей, ссылки на Evidence, entity resolution, retrieval и качество ответа. Для структуры считать precision/recall/F1 по типам, долю неверных оснований и неизвестных значений. Для retrieval — recall@k на синтетических вопросах; точные k/пороги выбираются на корпусе, не объявлены достигнутыми. Для советов — рубрика с примерами допустимого и недопустимого, без одного точного эталонного текста.

Корпус содержит отрицания, гипотезы, пересказ чужого опыта, неоднозначных людей, повтор одного эпизода, отсутствие данных и инструкции внутри цитат. Модель не должна принять фразу внутри дневника за системную команду или назначить медицинский диагноз. Изменение модели/prompt требует повторного прогона; сохраняются версия, параметры и агрегированные результаты без реальных разговоров.

## Предлагаемые gates

- Все обязательные проверки этапа проходят; skipped тест нельзя выдавать за passed.
- Для чистых критических политик — 100% покрытия ветвей на согласованных правилах; для Domain/Application — стартовая цель 90% строк и 85% ветвей. Значения предложены; исключения документируются, не маскируются глобальным exclude.
- Проверять значимые свойства property-based тестами: инверсия тревоги, границы баланса, идемпотентность, сумма проводок/переводов после определения финансовой модели.
- Mutation testing для критических формул до релиза: замена min на max, неверные пороги/время должны обнаруживаться. Числовой mutation threshold выбирается после baseline.
- Не использовать retries как средство скрыть падающий тест. Нестабильный тест имеет задачу, владельца и срок исправления; критический сценарий без замены блокирует релиз.
- Реальные медиа/данные не загружаются в отчёты CI. Скриншоты только синтетического стенда.

## Definition of Done

Требование связано с AC и тестом; правило размещено в правильном слое; новая реализация порта проходит contract suite; нужные миграции и восстановление проверены; CI зелёный на выпускаемом SHA; документация и диаграммы соответствуют изменению. Релиз включает журнал проверок и известных ограничений. Полный набор для ещё не реализованных модулей остаётся планом, а не выполненной проверкой.
