# План проектирования

> Baseline 1.0: нормативные значения и закрытые решения — [BR-01–10](../requirements/baseline-rules.md). Этот документ — вспомогательное представление; прежние пометки «предложено/уточнить» не отменяют зафиксированный baseline. Реализуемость интеграций подтверждается отдельными gates.

Статус: предложен. Не задаём сроки до определения доступного времени и глубины первой версии.

| Этап | Результат | Условие завершения |
| --- | --- | --- |
| 1. Исследование потребностей | Цели, сценарии дня, приоритеты, ограничения приватности | Согласованы результаты первой версии и её исключения |
| 2. Требования | ТЗ, словарь, примеры и критерии приёмки | Нет открытых вопросов, блокирующих основные сценарии |
| 3. Проверка реализуемости | Исследования API и небольшие технические эксперименты | Критические источники проверены либо выбраны альтернативы |
| 4. Логическое проектирование | Модель предметной области, UML, правила и временная семантика | Сценарии проходят через модель без противоречий |
| 5. Архитектура | C4, ADR, хранение, развёртывание, структура кода | Решены офлайн-работа, будущий бот, доступ и восстановление |
| 6. Проектирование интерфейса | Прототип основных экранов и ошибок | Проверен ежедневный путь пользователя и стоимость ввода |
| 7. Подготовка разработки | Вертикальные задачи, зависимости, риски, план проверок | Каждая задача связана с требованиями и приёмкой |

Этапы могут повторяться: ограничения интеграции способны изменить требования. Программирование продукта начинается после согласования достаточного набора решений; исследовательские эксперименты возможны раньше.

## Организация работы

- Использовать p3express как ориентир управления: обоснование, участники, результаты, риски, проверки и уроки. Полный процесс пока не утверждён.
- Kanban: «Идеи → Требует уточнения → Готово → В работе → Проверка → Готово и принято». Различать готовность к работе и завершение; для одного исполнителя предлагается одна основная задача в работе.
- Вести реестр рисков: доступность финансовых данных, работа бота без Mac, утрата чувствительных записей, неверная интерпретация состояния, избыточный ручной ввод, рост объёма проекта.
- Переход между этапами подтверждать результатами и согласованными решениями. Не считать существование диаграммы доказательством готовности архитектуры.

## Ближайшая работа

Разобрать по одному реальному сценарию расходов, состояния и привычек. На их основе согласовать состав первой версии и заполнить требования до выбора стека.
